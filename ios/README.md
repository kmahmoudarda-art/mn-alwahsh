# iOS app — what's here and what you need to do

This mirrors `ANDROID_HANDOFF.md`'s situation exactly: I wrote the
complete iOS project (Swift, StoreKit 2, all 71 in-app products wired up),
but **this cloud workspace has no macOS/Xcode**, so I can't generate the
`.xcodeproj`, build, sign, or submit it from here. Everything below is
exact copy-paste steps for doing that on your own Mac.

## What's here

- `App/` — a native `WKWebView` app (Swift, no third-party dependencies)
  that loads `https://mnalwahsh.com`, same site as the website and the
  Android app. Mirrors `android/app/.../MainActivity.kt`: splash screen,
  offline screen with retry, keeps your own pages inside the app and
  opens anything else in the system browser, landscape-only.
- `App/StoreKitBillingBridge.swift` — real Apple In-App Purchase (StoreKit
  2) code, exposed to the website as `window.WebkitBilling`, exactly like
  `AndroidBillingBridge.kt` exposes `window.AndroidBilling`. Nothing on
  the Android side changed — see `mn-alwahsh-updated/src/utils/platform.js`,
  `storeKitBillingClient.js`, and `CategoryPicker.jsx` for how the website
  picks whichever bridge is actually present at runtime.
- `netlify/functions/verify-apple-purchase.js` (in the website project) —
  the Apple equivalent of `verify-play-purchase.js`: re-verifies every
  purchase against Apple's own App Store Server API server-side before
  granting anything, using Apple's official
  [`@apple/app-store-server-library`](https://github.com/apple/app-store-server-library-node)
  npm package (already added to `mn-alwahsh-updated/package.json`).
- `project.yml` — an [XcodeGen](https://github.com/yonaskolb/XcodeGen)
  spec. XcodeGen generates the actual `.xcodeproj` from this file; you
  never hand-edit the generated project — you edit `project.yml` and
  regenerate. This is deliberate: a hand-written `.xcodeproj` (raw XML) is
  easy to corrupt and impossible for me to produce reliably without Xcode
  itself, whereas `project.yml` is a small, readable, diffable text file.
- `Configuration.storekit` — a local StoreKit testing config with **all
  71 products already filled in** (generated by
  `scripts/generate_storekit_config.mjs` from the same
  `playProducts.js` the Android app uses), so you can test purchases in
  the iOS Simulator/Xcode without touching App Store Connect at all.
- `scripts/generate_app_icons.py` — regenerates every app-icon size from
  `mn-alwahsh-updated/icon-512.png` (already run once; the PNGs are
  checked in under `App/Assets.xcassets/AppIcon.appiconset/`).

Product IDs are **shared 1:1** with the Android app's SKUs (`cat001`,
`cat002`, ..., `unlock_all_categories`, `trial_pass` — see
`playProducts.js`). You'll create the same 71 In-App Purchases in App
Store Connect with these exact IDs, which is also why the Netlify
function can just re-import `PLAY_PRODUCT_MAP` for categories/prices
rather than needing a second, drifting copy of that data.

## Phase 1 — Install the build tools (one-time, macOS only)

1. Install **Xcode** from the Mac App Store (needs macOS; there is no way
   around this for building/signing an iOS app — Apple only allows this on
   their own OS).
2. Install [Homebrew](https://brew.sh) if you don't have it, then:
   ```bash
   brew install xcodegen
   ```

## Phase 2 — Getting the project onto your Mac

1. Pull this branch from GitHub (`git clone`/`git pull`, or download as a
   ZIP and unzip).
2. You should now have, alongside `android/` and `mn-alwahsh-updated/`, an
   `ios/` folder.

## Phase 3 — Generate and open the Xcode project

```bash
cd path/to/mn-alwahsh/ios
xcodegen generate
open MnAlwahsh.xcodeproj
```

In Xcode:

1. Select the **App** target → **Signing & Capabilities**.
2. Under **Team**, pick your Apple Developer account (you need an active
   [Apple Developer Program](https://developer.apple.com/programs/)
   membership — $99/year — to submit to the App Store; a free account
   only lets you run on your own device for 7 days).
3. Set **Bundle Identifier** to whatever you actually register in the next
   step — the placeholder in `project.yml` is `com.mnalwahsh.ios`. If you
   change it, update `PRODUCT_BUNDLE_IDENTIFIER` in `project.yml` too (and
   re-run `xcodegen generate`) so the two never drift apart.

## Phase 4 — Register the app

1. [developer.apple.com](https://developer.apple.com) → **Certificates,
   Identifiers & Profiles** → **Identifiers** → **+** → register the exact
   Bundle ID from Phase 3 (e.g. `com.mnalwahsh.ios`). This is a **new,
   separate app** from the Android one — bundle IDs and Play package names
   are unrelated namespaces, so this doesn't need to match
   `com.mnalwahsh.twa`.
2. [App Store Connect](https://appstoreconnect.apple.com) → **Apps** → **+**
   → **New App** → iOS → pick the Bundle ID you just registered, fill in
   name (`من الوحش`), primary language (Arabic), SKU (anything unique,
   e.g. `mnalwahsh-ios`).
3. **Monetization → In-App Purchases** → create all 71 products (69
   category unlocks + the bundle + the trial). For each: pick
   **Non-Consumable** for every `catNNN` SKU and `unlock_all_categories`,
   **Consumable** for `trial_pass` — use the exact product ID strings from
   `playProducts.js`, and set whatever AED-equivalent price tier you want
   per `PLAY_PRODUCT_MAP`'s `price` field (Apple's own price picker
   converts to every storefront currency for you; there's no need to
   match Google Play's exact AED figure to the cent).
   This is the single most tedious step — there's no bulk-import UI for
   this in App Store Connect's web interface. Do it once, carefully.
4. **Users and Access → Integrations → In-App Purchase** (or "App Store
   Connect API", same page) → create an API key with at least the
   **App Manager** role → note the **Key ID** and **Issuer ID**, and
   download the `.p8` file (Apple only lets you download it once).

## Phase 5 — Wire up server-side verification (Netlify)

In your Netlify site's **Environment variables**, add:

| Variable | Value |
|---|---|
| `APPLE_ISSUER_ID` | Issuer ID from Phase 4 step 4 |
| `APPLE_KEY_ID` | Key ID from Phase 4 step 4 |
| `APPLE_PRIVATE_KEY` | Full contents of the downloaded `.p8` file, header included |
| `APPLE_BUNDLE_ID` | Your actual bundle id, e.g. `com.mnalwahsh.ios` |

Then push/merge this branch so `verify-apple-purchase.js` and the new
`@apple/app-store-server-library` dependency deploy — Netlify auto-builds
from the repo the same way it already does for the website.

**Never send me the `.p8` file's contents or paste them in this chat** —
they go directly into Netlify's env var UI, nowhere else.

## Phase 6 — Test purchases before submitting anything

**Local (Simulator, no App Store Connect products needed yet):**

In Xcode, **Product → Scheme → Edit Scheme → Run → Options → StoreKit
Configuration** → select `Configuration.storekit`. Run the app in the
Simulator — every one of the 71 products is already there, and purchases
succeed instantly with fake receipts. This exercises the full purchase UI
and bridge, but **skips real server verification** (there's no real
Apple transaction to verify) — don't rely on it to prove
`verify-apple-purchase.js` works.

**Sandbox (real App Store Server API round-trip, needs Phase 4 done):**

1. App Store Connect → **Users and Access → Sandbox → Testers** → add a
   sandbox Apple ID (any email you control, doesn't need to be real).
2. On a real device or the Simulator, build and run from Xcode (no
   StoreKit Configuration selected this time — let it hit the real,
   sandboxed App Store).
3. Sign into the sandbox Apple ID under **Settings → App Store →
   Sandbox Account** on the device (or when prompted mid-purchase).
4. Try unlocking a category — you'll see "Sandbox" in the system purchase
   sheet. This exercises the real path all the way through
   `verify-apple-purchase.js`.

## Phase 7 — Archive and upload to TestFlight

In Xcode: **Product → Archive** (only enabled when the run destination is
"Any iOS Device", not a Simulator). Once archived, the Organizer window
opens automatically → **Distribute App** → **App Store Connect** → follow
the prompts (it handles signing automatically if you picked your Team in
Phase 3). This uploads a build to App Store Connect / TestFlight — no
`.ipa` file to manually manage, unlike Android's APK/AAB.

Test via TestFlight on a real device before submitting for review.

## Phase 8 — Submit for App Store review

App Store Connect → your app → **App Store** tab → fill in the listing
(screenshots — landscape, since the app is landscape-only; description;
keywords; support URL; **privacy policy URL** — you already have
`mn-alwahsh-updated/src/pages/PrivacyPolicy.jsx`, link its live URL) →
**Add for Review** → pick the build you uploaded in Phase 7 → **Submit**.

Once the app exists, go back to
`mn-alwahsh-updated/src/components/game/CategoryPicker.jsx` and replace
the placeholder `https://apps.apple.com/app/id0000000000` with the real
App Store URL (App Store Connect shows it once the app is created — you
don't have to wait for approval to get the URL/id).

## Why this app should pass review — and what could still trip it up

Apple's most common rejection for an app like this is **Guideline 4.2
(Minimum Functionality)** — "your app is just a website in a wrapper."
Genuinely, that's structurally what this is, same as the Android app. What
mitigates it:

- Real native purchasing (StoreKit, not a web checkout) — Guideline 4.2.3
  specifically calls out apps that "simply wrap a website" as more likely
  to be approved when they also do something a browser tab can't, and
  native IAP is exactly that.
- No browser chrome (address bar, tabs) — feels like an app, not Mobile
  Safari.
- Native offline/error handling, launch screen, app icon, landscape lock.
- A working **Restore Purchases** flow (`restoreStoreKitPurchases()` in
  `storeKitBillingClient.js`, wired into `CategoryPicker.jsx`'s unlock
  modal) — required by Guideline 3.1.2 for non-consumable IAP, and now
  present.

Other things I already handled so they don't cause a rejection:

- **Guideline 3.1.1 (In-App Purchase)**: all digital content (category
  unlocks) goes through StoreKit, never a web-based payment — Apple
  requires this for digital goods, no way around it, same as Google.
- **Guideline 4.8 (Sign in with Apple)**: only required when an app offers
  third-party/social login (Google/Facebook/etc.) as an option. This app
  only has email/password (Supabase auth, no OAuth providers found in the
  codebase), so Sign in with Apple is **not** required here — don't add it
  unless you later add Google/Facebook login, at which point it becomes
  mandatory.
- **Export compliance**: `Info.plist` already sets
  `ITSAppUsesNonExemptEncryption = false` (the app only makes ordinary
  HTTPS calls), which skips the encryption question on every upload.
- **Privacy**: no camera, photo library, location, or file access is used
  (matches `ANDROID_HANDOFF.md`'s note that the app is "email/password
  login via Supabase, no camera/file upload/location"), so `Info.plist`
  needs no `NSCameraUsageDescription`-style purpose strings — I didn't add
  any that aren't used, which would itself be a rejection reason.
- **App Privacy "nutrition label"**: App Store Connect will still ask you
  to fill in the Privacy questionnaire by hand (data collected: account
  email via Supabase, purchase history) — I can't fill that in for you
  since it's answered in App Store Connect's UI, not a repo file.

What I can't de-risk from here: Apple's human reviewers are inconsistent
about wrapper apps regardless of how much native functionality is added.
If it's rejected under 4.2 anyway, the Resolution Center will say so
specifically — the fastest fix is usually adding one more clearly-native
touch (e.g. native share sheet, native haptics on correct answers) and
resubmitting with a reviewer note explaining the real IAP + native chrome
already present.
